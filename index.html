1Objective

This project is a hands-on lab built to learn and demonstrate three things:

  • Progressive canary deployments. Traffic moves to a new version in steps. The release is promoted if it stays healthy and rolled back automatically if it does not.
  • A zero-downtime EKS version upgrade from Kubernetes 1.34 to 1.35.
  • A complete GitOps CI/CD pipeline around both.

The workload is recharge-system, a static “QuickCharge” web page (HTML and Tailwind) served by nginx. It is deliberately simple so that every moving part in the delivery path is the subject of the lab.

How to reproduce this POC

Read top to bottom — the sections are in build order. The shortest path for a repeat run:

  1. Get the SCP exclusion + IAM permissions in place (§4) — this is the single biggest blocker on a restricted account.
  2. Create the S3 state backend (§5), then terraform apply for infra (§6).
  3. Install the Load Balancer Controller (§7), push the GitOps repo and flux bootstrap (§8).
  4. Flux deploys NGINX, Flagger, Prometheus, Jenkins and the app automatically.
  5. Set up the Jenkins pipeline in the UI (§11), run a build, watch the canary promote (§10).
  6. Practise the version upgrade (§12), then tear down (§14).

Once the repos exist, a full rebuild is one command: export GITHUB_TOKEN=<pat> && ./scripts/resume.sh. Everything is in Git, so the environment is fully reproducible — it was torn down and rebuilt several times during the lab. Watch for the five gotchas flagged in §15; they recur on rebuilds if not committed to Git.

4.3Permissions: IAM and the SCP

Two layers decide whether a call succeeds. IAM policies grant actions to a principal. A service control policy (SCP) is an organization-level guardrail that can only restrict, and an explicit SCP deny overrides any IAM allow. Fixing an SCP deny therefore needs the management-account administrator.

In this account the SCP p-jqf3wzw9 denies eks:* and ecr:* unless the principal is excluded. These principals were excluded:

PrincipalCondition keyPattern
Your useraws:userid*:nipur@cloudthat.com
EKS node roleaws:PrincipalArnarn:aws:iam::821410798987:role/default-eks-node-group-*

Wildcard patterns survive rebuilds, which is why the node role is excluded by pattern. Alongside the SCP, the IAM role needs companion actions for tagging, describing, iam:PassRole and optional KMS. They are listed in missing-permissions-policy.json, the file to hand to an administrator.

4.4Credential model

No static keys exist anywhere. Pods receive AWS credentials in one of two ways: IRSA, a role bound to a service account through the cluster's OIDC provider, or the node's instance role. The lab uses IRSA for the two controllers and the node role for Jenkins builds, because the node role was already SCP-excluded and refreshes itself.

5Terraform remote state

State lives in S3 with versioning and native lockfile locking, so no DynamoDB table is needed (Terraform 1.10 or later).

bash
BUCKET=ct-eks-canary-tfstate-821410798987
aws s3api create-bucket --bucket $BUCKET --region ap-south-1 \
  --create-bucket-configuration LocationConstraint=ap-south-1
aws s3api put-bucket-versioning --bucket $BUCKET --versioning-configuration Status=Enabled

setup-tf-backend.sh performs these two calls and also writes backend.tf:

backend.tf
terraform {
  backend "s3" {
    bucket       = "ct-eks-canary-tfstate-821410798987"
    key          = "eks-canary-practice/terraform.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true   # native S3 locking, no DynamoDB
  }
}
bash
cd terraform/environments/practice
terraform init -migrate-state

7AWS Load Balancer Controller

Terraform created the IRSA role. The controller is installed with Helm against a service account that is created first and annotated with that role.

LBC_ROLE=$(terraform output -raw lb_controller_role_arn)
VPC_ID=$(aws eks describe-cluster --name $CLUSTER --region $R \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text)

kubectl create serviceaccount aws-load-balancer-controller -n kube-system
kubectl annotate serviceaccount aws-load-balancer-controller -n kube-system \

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=$CLUSTER \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=$R --set vpcId=$VPC_ID

kubectl -n kube-system rollout status deployment/aws-load-balancer-controller

The Git repo is the single source of truth and Flux continuously reconciles the cluster to match it. Flux watches only the GitOps repo, never the app repo. CI bridges the two by committing an image tag, so Jenkins never runs kubectl apply.

The eks-canary-gitops repo is laid out like this:

9.3Manifests

Under apps/recharge-system/:

  • deployment.yaml: image podinfo:recharge-v1.0.0, port 80, /healthz probes. It sets no replica count because Flagger manages it.
  • hpa.yaml: minimum 2, maximum 4.
  • canary.yaml: MetricTemplate, Canary and Ingress, described in section 10.
  • traffic-generator.yaml: an always-on curl loop that keeps metrics steady.

After commit and push, Flux deploys the files and Flagger initializes. The sign of success is a recharge-system-primary deployment appearing.

9.4Reaching the app from a browser

The NGINX Service creates the NLB, which is internal by default. Two annotations on the controller Service make it public:

yaml
# infrastructure/nginx.yaml, controller.service.annotations
service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"

Flagger's NGINX canary needs a host on the ingress, so the ingress uses recharge.example.com, which has no real DNS. Pick one way to browse:

  • Add <NLB_IP> recharge.example.com to the hosts file of the machine that runs the browser.
  • Port-forward the primary service: kubectl port-forward -n recharge-system svc/recharge-system-primary 8080:80.

In production the host would be a Route 53 record pointing at the NLB. See the host and DNS issue for why the host cannot simply be dropped.

10Canary with Flagger

Concept

Flagger creates a -primary copy of the Deployment, shifts traffic in weighted steps through NGINX, gates each step on Prometheus metrics, then promotes or rolls back on its own. It needs three things to work: a traffic router (NGINX), metrics (Prometheus) and traffic (the loadtester and traffic-generator).

Without steady traffic, rate() over a one-minute window has too few samples and the metric comes back empty, which Flagger reads as a failure. That is why the lab runs an always-on traffic source.

10.1Custom metric template

Flagger's built-in NGINX query filters on exported_namespace, but this cluster's metrics carry namespace. The custom query below uses the right label and returns 0% error when there is no traffic, instead of NaN.

MetricTemplate query
100 - (
  sum(rate(nginx_ingress_controller_requests{namespace="{{namespace}}",ingress="{{target}}",status!~"5.."}[{{interval}}]))
  /
  sum(rate(nginx_ingress_controller_requests{namespace="{{namespace}}",ingress="{{target}}"}[{{interval}}]))
  * 100
) or on() vector(0)

10.2Canary spec

canary.yaml
analysis:
  interval: 30s
  threshold: 5
  maxWeight: 50
  stepWeight: 10
  metrics:
    - name: nginx-success-rate          # templateRef to the custom template
      thresholdRange: { max: 10 }
      interval: 2m
  webhooks:
    - name: load-test                   # continuous: hey -z 5m -q 50 -c 10 through the ingress
SettingValueMeaning
stepWeight10Traffic added to the canary at each step
maxWeight50Weight reached before promotion
interval30sHow often Flagger evaluates
threshold5Failed checks tolerated before rollback
thresholdRange.max10Maximum error rate in percent. Started at 5, raised to 10 to absorb low-traffic noise that peaks at the 50% hold.
metrics.interval2mMetric window, widened from 1m so brief spikes average out
What actually happened

The first real rollout climbed cleanly to 50% and then rolled back at the promotion hold. The app was healthy, serving only 200s. The cause was metric noise: at 50% weight more traffic hits fresh canary pods, so transient 404/503 blips pushed the measured error rate to 5–8%, just over the original 5% limit. In a low-traffic lab a handful of stray requests swings the percentage wildly; in production the same errors would be a fraction of a percent. The fix was to raise the threshold to 10%, widen the window to 2m, and run a stronger always-on traffic generator so clean 200s dominate. The next rollout promoted at an error rate around 5–7%, comfortably under the new limit.

10.3Trigger a canary

Bump the image tag in the GitOps deployment.yaml and push, or patch the Deployment directly for a quick test:

bash
kubectl -n recharge-system set image deployment/recharge-system recharge-system=<new-tag>
kubectl -n recharge-system get canary recharge-system -w
# phases: Initialized, Progressing (10 to 50), Promoting, Succeeded

A deliberately bad version shows the other path: after five failed checks the status becomes Failed and all traffic returns to the primary.

11CI with Jenkins

Jenkins runs inside the cluster. Build pods authenticate to ECR with the node role, so there are no stored keys and nothing that expires hourly.

11.1Storage prerequisite: EBS CSI

Jenkins needs a persistent volume. From EKS 1.34 the in-tree EBS provisioner is gone, so the EBS CSI add-on and a CSI-based default StorageClass are required (what happens without them). The StorageClass lives in the GitOps repo (infrastructure/storageclass.yaml) so it is recreated on every rebuild — applying it by hand once was the mistake that broke a later rebuild.

hcl
# environments/practice/main.tf — declared at the root (after the iam module)
# to avoid a cluster↔iam OIDC dependency cycle.
resource "aws_eks_addon" "ebs_csi" {
  cluster_name             = module.cluster.cluster_name
  addon_name               = "aws-ebs-csi-driver"
  service_account_role_arn = module.iam.ebs_csi_role_arn
}
bash
kubectl apply -f - <<EOF
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3, annotations: { "storageclass.kubernetes.io/is-default-class": "true" } }
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters: { type: gp3 }
EOF
kubectl patch storageclass gp2 -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"false"}}}'

11.2Deploy Jenkins through Flux

infrastructure/jenkins.yaml is a HelmRelease of the jenkins 5.x chart in namespace jenkins, with agents enabled and an 8 Gi persistent volume. The ingress is deliberately disabled: the AWS Load Balancer Controller admission webhook validates every ingress and rejects the Jenkins one on a fresh cluster because the nginx IngressClass is not yet registered when the chart installs. Access is via port-forward instead.

infrastructure/jenkins.yaml (key values)
controller:
  ingress:
    enabled: false                 # avoids the LBC webhook conflict; use port-forward
  installPlugins:
    - kubernetes:latest
    - workflow-aggregator:latest
    - git:latest
    - configuration-as-code:latest
    - pipeline-stage-view:latest
  persistence: { enabled: true, size: 8Gi }     # needs the gp3 StorageClass above
agent: { enabled: true, namespace: jenkins }
serviceAccount:      { create: true, name: jenkins }
serviceAccountAgent: { create: true, name: jenkins-agent }   # no IRSA: build pods inherit the node role

11.4Add the GitHub credential (UI)

Jenkins needs a token to push the image-tag commit to the GitOps repo.

  1. Manage Jenkins → Credentials.
  2. Open the System store → Global credentials (unrestricted) → Add Credentials.
  3. Kind: Secret text. Secret: your GitHub PAT with repo scope. ID: github-token (must match the Jenkinsfile exactly). Save.

11.5Create the pipeline job (UI)

  1. New Item → name recharge-system → Pipeline → OK.
  2. In Pipeline: Definition = Pipeline script from SCM; SCM = Git.
  3. Repository URL: https://github.com/NipurJain4/recharge-system.git; Branch: */main; Script Path: Jenkinsfile.
  4. Optional auto-trigger: Build Triggers → Poll SCM, schedule H/2 * * * * (checks every ~2 min and builds only when there is a new commit). Do not paste a pipeline { ... } snippet into the UI — that belongs in the Jenkinsfile, not a config box.
  5. Save, then Build Now for the first run (sets the poll baseline).

11.6The pipeline

The Jenkinsfile in the app repo runs on a Kubernetes agent pod with two containers — kaniko (build) and a git image (commit). Stage one builds with Kaniko, because build pods have no Docker daemon, and pushes to ECR as recharge-b<BUILD_NUMBER> using the node role. Stage two clones the GitOps repo, rewrites the image tag in apps/recharge-system/deployment.yaml with sed, then commits and pushes. Flux and Flagger take over from there.

The complete path was verified end to end with a visible change on the page: code push, Jenkins build, ECR, tag commit, Flux, Flagger canary, live.

12EKS version upgrade, 1.34 to 1.35

EKS allows one minor version at a time. The control plane can run one minor ahead of the nodes and never behind. Nodes are replaced rather than upgraded in place, which is what makes zero downtime possible.

12.1Pre-flight

bash
aws eks describe-cluster --name eks-canary-practice --region ap-south-1 --query 'cluster.version'
kubectl get nodes
aws eks describe-cluster-versions --region ap-south-1 \
  --query 'clusterVersions[].clusterVersion' --output text      # confirm 1.35 is available
kubectl get pods -A | grep -vE "Running|Completed"              # baseline should be empty

12.2Upgrade

Change cluster_version from "1.34" to "1.35" in terraform/environments/practice/terraform.tfvars. The add-ons use most_recent = true, so they move to 1.35-compatible versions in the same apply.

bash
cd terraform/environments/practice
terraform plan     # expect only "updated in-place": cluster, node group, add-ons
terraform apply    # about 25 to 30 min in total

12.3Watch from a second terminal

bash
kubectl get nodes -w                      # old 1.34 nodes drain, new 1.35 nodes join
kubectl get pods -n recharge-system -w    # the app stays up
aws eks describe-cluster --name eks-canary-practice --region ap-south-1 --query 'cluster.version'

12.4Verify

bash
kubectl get nodes                                         # all v1.35.x
kubectl get pods -A | grep -vE "Running|Completed"        # nothing broken

13.3What the dashboard shows

Lesson: match the dashboard to the mesh

The popular community dashboard (Grafana.com ID 15158) is written for Flagger with Istio, so its request-rate, success-rate and latency panels query istio_requests_total. This lab routes with NGINX, whose metrics are nginx_ingress_controller_requests, so those panels show “No data” even though the data exists under different names. The weighting and status panels still work because they read Flagger's own metrics, and CPU/memory work from cAdvisor. For a fully populated view on an NGINX setup, build a small custom dashboard whose panels query nginx_ingress_controller_requests — the same metric the canary's success-rate template uses.

A related earlier gotcha: the first dashboard ID tried, 9657, turned out to be an etcd dashboard, not Flagger. Always confirm the Grafana.com dashboard ID matches the tool before provisioning.

Access and policy

SCP blocks EKS and ECRrecurring

Symptom

Calls fail with explicit deny in a service control policy. Plain IAM gaps read no identity-based policy allows instead, which is how the two are told apart.

Cause

Org SCP p-jqf3wzw9, in management account 775267928995, denies eks:* and ecr:*. IAM cannot override it. It returned for each new principal: first the user role, then the node role, and it would have for a Jenkins role.

Fix

The administrator adds exclusions with NotLike conditions on aws:userid and aws:PrincipalArn. Use wildcard patterns so rebuilds stay covered.

Canary and metrics

Canary always rolled back on a healthy appcanary

Symptom

Flagger rolled back with no values found for nginx metric request-success-rate while every request returned HTTP 200.

Cause
  1. Prometheus scraped every 1 minute but the query used rate(...[1m]). One sample per window, and rate() needs at least two.
  2. The built-in query filters on exported_namespace, but the metrics carry namespace.
  3. The loadtester sent bursts with gaps, and stray 404 and 504 responses spiked the error rate during the gaps.
Fix
  1. Scrape every 15 s so a one-minute window holds about four samples.
  2. Use the custom MetricTemplate from section 10.1.
  3. Run the always-on traffic-generator, a longer higher-concurrency loadtester, and a 5% error threshold.

Result: clean promotion on good versions, and rollback still fires on genuinely bad ones.

Success-rate query returned NaNcanary

Symptom

The metric intermittently evaluated to NaN while debugging.

Cause

When traffic dropped to zero the formula divided 0 by 0.

Fix

The or on() vector(0) fallback in the template turns no traffic into 0% error. Continuous traffic keeps the window populated.

18Lessons

  1. When IAM looks right and calls still fail, look for an SCP deny. Every new principal that needs EKS or ECR may need its own exclusion.
  2. Canary metrics are timing-sensitive. The scrape interval must sit well under the query window, and the canary needs continuous traffic.
  3. From EKS 1.34 the EBS CSI add-on is mandatory for persistent volumes.
  4. Match where CI runs to how it authenticates. In-cluster CI with the node role removed stored keys and expiry.
  5. Keep app and GitOps in separate repos and let CI bridge them with an image tag commit.
  6. terraform import and state rm are how a partial apply is recovered.
  7. Zero-downtime upgrades need gradual node replacement, more than one replica and a sensible surge setting.
